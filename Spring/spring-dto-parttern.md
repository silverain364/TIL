# DTO 패턴 : Entity를 직접 주고 받으면 안 되는 이유
DB 구조와 API 응답 구조는 다를 수 있다. DTO가 그 다리 역할을 한다. | 2026-10-12

### DTO가 뭐지?
DTO는 계층 간 데이터를 주고받기 위한 전용 객체다.
클라이언트가 보내는 요청을 담는 Request DTO, 클라이언트에게 돌려주는 응답을 담는 Response DTO로 나뉜다.
Entity와 분리함으로써 API 스펙과 DB 구조를 독립적으로 관리할 수 있다.

### 데이터 흐름
`클라이언트` → `Request DTO` → `Entity` → `Response DTO` → `클라이언트`
요청이 들어오면 Request DTO로 받고, Service에서 Entity로 변환해 DB에 저장한다.</br>
웅답을 줄 때는 Entity를 Response DTO로 변환해서 필요한 정보만 골라 내려준다.</br>
Entity 자체가 API를 타고 나가는 일은 없어야 한다.

### Entity를 직접 변환하면 안 되는 이유
Entity를 그대로 클라이언트에 내려주면 여러 문제가 생긴다.</br>
첫 번째로는 민감한 정보를 노출한다. 비밀번호, 내부 식별자 등 클라이언트에게 줘선 안 되는 필드까지 다 나간다.</br>
두 번째로는 순환 참조이다. JPAA 연관관계에서 User → Order → User... 처럼 무한 루프가 발생해 JSON 직렬화가 터질 수 있다.</br>
세 번째론 API와 DB 구조가 강결합된다. DB 컬럼명이 바뀌면 API 스펙도 같이 바뀌는 문제가 생긴다.

> Request DTO와 Response DTO를 분리해야 된다. 하나의 DTO로 요청과 응답을 모두 처리하기보단, 요청에 필요한 필드와 응답에 담을 필드는 다른 경우가 많다. 처음부터 분리해두면 나중에 확장할 때 훨씬 편하다.<br/>

> Entity에서 DTO 변환하는 로직을 확장 함수로 만들면 변환 코드가 깔끔하게 정리된다. 이 두 개념이 Spring + Kotlin 실무에 항상 함께 쓰인다.
